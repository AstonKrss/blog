# 性能优化结果汇总

> 最后更新：2026-11-10
> 说明：本文件只汇总已有报告的结果，不把不同数据规模、不同部署拓扑的实验直接拼成一个“总提升百分比”。

---

## 1. 结果可信度分级

| 级别 | 含义 |
|---|---|
| A | 有真实接口、固定数据、可复现实验和原始结果 |
| B | 有应用日志、数据库指标或真实故障演练 |
| C | 只有单元/集成测试或单次烟测 |
| D | 设计存在，但尚未端到端验证 |

本项目的原则是：

> 性能结论必须带场景；高可用结论必须带故障演练；未验证项不能写成已上线能力。

## 4. Redis 与缓存可靠性

| 项目 | 结果 |
|---|---|
| Redis 停止后文章列表 | HTTP 200，回源 MySQL |
| Redis 停止后标签接口 | HTTP 200，回源 MySQL |
| 文章详情缓存 fallback | 指标出现，接口可继续返回 |
| 在线人数 Redis 故障 | 返回 0 |
| 留言限流 Redis 故障 | fail-open，留言仍可用 |
| 登录防护 Redis 故障 | fail-open，登录不变成 500 |
| 浏览量 Redis 故障 | 允许少计，不阻断页面 |

证据：

- `CACHE_RESILIENCE.md`
- `REDIS_FAILURE_POLICIES.md`
- `CACHE_AND_HOT_WRITE_REPORT.md`

边界：

- Redis 故障期间数据库压力上升；
- 热点 Key 跨实例不是严格全局单飞；
- 缓存写回失败只记录指标，不阻断业务。

## 5. RabbitMQ 可靠异步

| 验证项 | 结果 |
|---|---|
| 正常投递 | 消息写入 `visit_logs` |
| 重复 eventId | 数据库仍只有 1 行 |
| RabbitMQ 停止 30 秒 | 10/10 业务请求 HTTP 200，publish failure 增加 |
| RabbitMQ 恢复 | 消费者自动重连，消息继续落库 |
| 批量消费 | batch size 20，20 条全部落库 |
| 非法消息 | 进入 `visit.log.write.dlq` |
| DLQ 重放 | 修复 eventId 后重新投递成功 |
| 优雅停机 | Rabbit listener 和 Web 容器均 graceful shutdown |

证据：`RABBITMQ_VISIT_LOG.md`。

边界：

- 生产端 fail-open，故障期间日志可能丢失；
- 事件零丢失需要 Outbox；
- 批量重试是进程内重试，不是独立延迟重试队列。

## 6. 单实例 / 双实例资源隔离实验

### 6.1 背景

在只有一台电脑的情况下，直接启动两个 JVM 并不会自动获得两份 CPU。因此本实验增加了：

- k6 CPU 亲和性：CPU 0-3；
- backend-1：CPU 8-11；
- backend-2：CPU 12-15；
- MySQL、Redis、RabbitMQ、Nginx 仍未完整隔离；
- k6 与被测系统仍在同一台机器。

### 6.2 缓存开启

| 目标 RPS | 模式 | 实际 RPS | P95 | Dropped |
|---:|---|---:|---:|---:|
| 1000 | 单实例两轮 | 904.89 / 958.00 | 2076.98 / 1284.92 ms | 2107 / 948 |
| 1000 | 双实例两轮 | 999.83 / 999.91 | 63.95 / 45.02 ms | 0 / 0 |
| 1500 | 单实例两轮 | 1499.86 / 1409.17 | 26.39 / 1935.43 ms | 0 / 1320 |
| 1500 | 双实例两轮 | 1499.84 / 1460.57 | 5.17 / 6.92 ms | 0 / 0 |

### 6.3 缓存关闭

| 目标 RPS | 模式 | 实际 RPS | P95 | Dropped |
|---:|---|---:|---:|---:|
| 200 | 单实例 | 199.99 | 64.86 ms | 0 |
| 200 | 双实例 | 200.01 | 8.86 ms | 0 |
| 500 | 单实例两轮 | 498.38 / 495.21 | 73.79 / 475.91 ms | 47 / 143 |
| 500 | 双实例两轮 | 499.97 / 499.97 | 8.69 / 273.87 ms | 0 / 0 |

### 6.4 正确结论

可以写：

> 在单机 CPU 资源隔离实验中，双实例在 1000/1500 RPS 下均无 dropped iterations；单实例多次出现 dropped iterations 和长尾延迟，说明应用层复制在获得额外 CPU 预算后能改善稳定性。

不能写：

> 双实例性能提升 100%。

不能写：

> 单机实验证明两台服务器可以线性扩容。

证据：`BENCHMARK_PHASE4_SCALING.md`。

## 8. 简历安全表述

建议选择 2～3 条，不要堆满。

### 查询与缓存

> 针对文章分页、笔记 N+1 和 LIKE 全表扫描，基于 5 万文章、20 万标签关联、10 万评论数据完成两段式分页、批量加载、索引和 FULLTEXT 改造；文章列表 P95 从 6.78s 降至 3.14ms，笔记列表 SELECT 从约 42 次/请求降至 4 次/请求。

### Redis 与可靠性

> 实现 Redis 缓存统一故障降级、TTL 抖动、精确失效、热点 Key 回源保护和浏览量幂等落库；文章列表/搜索缓存命中率分别达到 99.95%/99.98%，Redis 停止时核心页面可回源 MySQL。

### RabbitMQ

> 使用 RabbitMQ 解耦访问日志写入，实现 Publisher Confirm、手动 ACK、批量消费、eventId 幂等、有限重试和 DLQ；RabbitMQ 停止 30 秒期间业务请求全部 HTTP 200，恢复后消费者自动重连并继续落库。

### 多实例

> 基于 Nginx + 双 Spring Boot 实例验证无状态部署和单实例故障转移；通过 CPU 亲和性隔离进行固定到达率压测，双实例在 1000/1500 RPS 下无 dropped iterations，并明确区分单机资源隔离实验与真实多机扩容的边界。

## 9. 面试时必须主动说明的限制

- 本机压测不能直接等同生产容量；
- k6 和被测系统共享单台电脑；
- 两个 JVM 不等于两份硬件资源；
- MySQL 是当前主要单点；
- RabbitMQ 生产端 fail-open，可能丢访问日志；
- MinIO 真实共享文件验收尚未完成；
- 热点 Key 跨实例不是严格全局单飞；
- 缓存关闭时数据库路径会明显饱和。

能主动说清这些限制，比给出一个没有条件的“高性能”结论更可信。
