## ADR-001：保持模块化单体

**状态：** 已采纳

**背景：**

- 当前是个人博客，业务边界相对清晰；
- 没有独立团队、独立扩缩容和跨团队发布需求；
- 直接拆微服务会引入服务发现、分布式事务、链路追踪和部署复杂度。

**决策：**

保持 Spring Boot 模块化单体，通过包边界和业务模块隔离职责。

**收益：**

- 本地开发、测试、部署简单；
- 事务和排障成本低；
- 可以先完成性能、缓存、MQ 和可靠性改造。

**代价：**

- 单体发布粒度较大；
- 未来某些模块需要独立扩容时，仍需再做服务拆分。

## ADR-002：搜索先使用 MySQL FULLTEXT，不引入 Elasticsearch

**状态：** 已采纳

**背景：**

- 当前搜索需求以标题、内容、标签为主；
- 数据规模在 MySQL 可处理范围内；
- ES 需要额外集群、索引同步和双写/补偿机制。

**决策：**

为 `title`、`content` 增加 FULLTEXT 索引，标签使用 EXISTS 或独立关联查询。

**收益：**

- 运维简单；
- 不存在 MySQL/ES 双写一致性；
- 当前数据量下能获得可接受的查询计划。

**代价：**

- 中文分词、相关性排序、复杂聚合能力有限；
- 数据量或搜索复杂度上升后需要重新评估 ES/OpenSearch。

## ADR-003：核心页面缓存采用 Redis，并允许故障时回源 MySQL

**状态：** 已采纳

**背景：**

Spring Cache 默认在 Redis 连接失败时可能直接抛异常，导致方法体不执行。

**决策：**

增加统一 `ResilientCacheManager`：

- Redis 命中直接返回；
- Redis miss 执行 loader；
- Redis get 失败记录指标并执行 loader；
- Redis 写回失败不影响业务返回。

**收益：**

- Redis 故障时文章列表、详情、标签等核心页面仍可访问；
- 降级行为集中，不散落在每个 `@Cacheable` 方法里。

**代价：**

- Redis 故障时数据库压力明显上升；
- 缓存回源失败指标需要告警。

## ADR-004：热点 Key 跨实例采用“可用性优先”的互斥回源

**状态：** 已采纳

**背景：**

单实例可以通过本地锁保证同一热点 Key 只有一个请求回源；多实例还需要 Redis 分布式锁。

**决策：**

- 单实例内强互斥；
- 多实例尝试 Redis 锁；
- 未抢到锁的实例不无限等待，允许继续执行 loader；
- 写缓存后释放锁，释放时比较 token。

**收益：**

- 避免一个实例短时间重复回源；
- 不会因为 Redis 锁等待导致请求全部卡死；
- 交易型缓存场景下保持可用性。

**代价：**

- 跨实例仍可能少量重复回源；
- 全局严格单飞需要引入等待、二次检查和超时取消。

## ADR-005：只为访问日志引入 RabbitMQ

**状态：** 已采纳

**背景：**

访问日志写入是典型的可异步、可容忍短暂失败的低优先级链路。

**决策：**

只把 `visit_logs` 写入异步化：

```text
blog.events (direct)
  -> visit.recorded
  -> visit.log.write
  -> visit.log.write.dlq
```

不把邮件、点赞、缓存失效、搜索索引全部塞进 MQ。

**收益：**

- 业务请求不等待日志落库；
- 可以用一条链路完整验证生产者确认、消费者 ACK、DLQ 和幂等；
- 系统复杂度可控。

**代价：**

- 访问日志不是强一致；
- 生产端 fail-open 时可能丢日志。

## ADR-006：访问日志采用 Publisher Confirm + 手动 ACK + eventId 幂等

**状态：** 已采纳

**背景：**

MQ 通常是 at-least-once，生产者重试和消费者重连都可能产生重复消息。

**决策：**

- Producer 生成稳定 `eventId`；
- 发送持久化消息并使用 Publisher Confirm；
- Consumer 在 MySQL 事务提交后手动 ACK；
- `visit_logs.event_id` 唯一约束兜底幂等；
- 批量事务失败时二分拆批；
- 重试耗尽后进入 DLQ。

**收益：**

- Broker 接收和业务落库分别有明确确认；
- 重复消息不会重复写库；
- 坏消息隔离，不阻塞正常批次。

**代价：**

- Publisher Confirm 不等于消费者完成；
- 批量事务失败时可能使部分正常消息重试；
- 当前重试是进程内重试，不是独立延迟队列。

## ADR-007：文章列表采用两段式分页

**状态：** 已采纳

**背景：**

`JOIN FETCH` 集合关联和 `Page` 一起使用时，Hibernate 可能对集合做内存分页，数据量大时性能不可控。

**决策：**

1. 先用不加载集合的查询获取当前页文章 ID；
2. 再按 ID 批量加载作者、标签等关联；
3. 按 ID 顺序组装 VO。

**收益：**

- 避免集合 JOIN 导致计数和分页异常；
- 查询次数可控；
- 适合读多写少和缓存场景。

**代价：**

- 需要额外一次或多次批量查询；
- 组装逻辑比单条 JPQL 更复杂。

## ADR-008：浏览量使用 Redis 增量 + MySQL 幂等落库

**状态：** 已采纳

**背景：**

每次浏览都直接更新 MySQL 会放大小写入压力；先 MySQL 后 Redis 又无法组成跨系统原子事务。

**决策：**

- Redis 累积浏览量；
- 定时任务生成稳定 `batchId`；
- MySQL `INSERT` batchId 唯一记录，成功后原子更新文章计数；
- 扣减 Redis 增量；
- Redis 故障时允许少计。

**收益：**

- 降低 MySQL 写频率；
- 重复执行不会重复加浏览量；
- 崩溃恢复可以基于 batchId 判断是否已处理。

**代价：**

- 浏览量不是实时强一致；
- Redis 故障期间可能少计。

## ADR-009：多实例保持无状态，文件存储可选 MinIO

**状态：** 部分验证

**背景：**

两个后端实例共享数据库和 Redis，但本地 `uploads/` 目录无法跨机器共享。

**决策：**

- JWT 无状态，不使用 Sticky Session；
- 文件存储抽象为 `FileStorage`；
- 本地模式保留开发便利；
- 多实例模式切换 MinIO。

**收益：**

- 后端可以复制；
- 上传文件不依赖单台机器本地路径。

**代价：**

- MinIO 真实上传、双实例读取和故障接管尚未完成端到端验收；
- 本地模式仍只适合单机。

## ADR-010：双实例和高可用优先于“单机虚假扩容”

**状态：** 已采纳

**背景：**

一台电脑上启动两个 JVM，不等于获得两份 CPU、网卡和 MySQL。

**决策：**

- 双实例首先用于验证无状态部署、Nginx 分流和故障切换；
- 真实性能结论必须结合 CPU 亲和性、压测机和共享中间件；
- 不在单机测试中宣称线性扩容。

**收益：**

- 结果可解释；
- 面试时能够区分高可用、水平扩展和性能提升。

**代价：**

- 需要额外机器才能完成生产级扩容证明；
- 部分结论保留为延期项。

## ADR-011：暂不引入 Kafka、Kubernetes、Nacos

**状态：** 已采纳

**背景：**

当前规模没有对应的真实问题。

**决策：**

- 单条访问日志链路使用 RabbitMQ；
- 使用 Nginx + 两个实例演示水平扩展；
- 配置使用环境变量；
- 暂不引入 Kafka、K8s、Nacos。

**收益：**

- 避免组件堆叠；
- 每个组件都有明确问题和验证目标；
- 面试时能讲清“为什么不用”。

**代价：**

- 未来真实流量增长后需要重新评估消息吞吐、服务发现和容器编排。
