Hot key lab / Cache stampede

缓存失效的一瞬间，谁去查数据库？

热点 Key 防击穿的目标不是“让缓存永不失效”，而是让大量并发请求同时发现缓存未命中时，不要一起冲向 MySQL。这个实验展示你项目里的实际实现，以及它的边界。

01 / mental model

缓存击穿是什么

Cache hit

缓存有值，直接返回，不查数据库。

Cache miss

缓存没值，一个请求应该回源数据库。

Stampede

缓存刚过期，大量请求同时 miss，一起查数据库。

Mutex

只让一个请求执行 loader，其他请求等待或稍后重新读缓存。

你项目里的关键顺序： 
ResilientCache.get(key, loader)
  -> 查缓存
  -> CacheStampedeGuard.load(...)
      -> 本地锁
      -> 尝试 Redis 锁
      -> 二次检查缓存
      -> loader.call()  // 查 MySQL
      -> put(key, value)
      -> 释放锁

05 / strict mode

    
如果要严格跨实例互斥，代码要加什么？

    
当前实现故意没有让拿不到 Redis 锁的实例阻塞，因为那会把锁故障或锁竞争转换成 HTTP 延迟。严格互斥的骨架通常是：

    

      
本地锁
  -> 获取缓存
  -> 尝试 Redis 锁
  -> 如果没拿到：
       轮询等待锁释放 / 短暂 sleep
       重新检查缓存
       超时后降级回源
  -> 拿到锁的请求执行 loader
  -> 写缓存
  -> 释放锁

    

    

      
方案数据库回源请求延迟故障行为

      
        
当前：本地锁 + 尝试 Redis 锁单实例 1 次，多实例可能 2 次通常不额外等待Redis 故障时仍然可用

        
严格：等待 Redis 锁跨实例通常 1 次可能增加几十到几百毫秒需要设置等待上限和超时降级

        
只使用 Spring `sync=true`只保护当前 JVM低多实例仍可能重复回源

      
    

    
这也是为什么页面要同时展示“当前实现”和“严格互斥设想”：两者不是同一个可靠性级别。
