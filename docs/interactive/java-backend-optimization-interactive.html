k6 固定到达率脚本怎么运行？

阶段 0：可观测性与压测基线

先回答“系统现在到底怎么样”，否则加缓存、加机器、加 MQ 都可能只是猜。

Actuator 是什么？

Spring Boot 提供的管理和观测端点。比如 /actuator/health 查看健康状态，/actuator/prometheus 暴露指标。它不是 Prometheus 本身，只是把指标“拿出来”。

Micrometer 是什么？

Java 应用的指标门面。业务和框架通过它记录 counters、timers、gauges，再转换成 Prometheus 格式。它像“指标 SDK + 适配层”。

Prometheus 是什么？

时序数据库和抓取系统。它定时访问 /actuator/prometheus，保存 CPU、请求延迟、连接池等时间序列，并支持 PromQL 查询和告警。

Grafana 是什么？

可视化面板。它不负责采集，而是查询 Prometheus，把 P95、JVM、Hikari、Redis、RabbitMQ 指标画成图。

指标如何从应用走到 Grafana？

Spring Boot业务代码 / Tomcat / Hikari
→
Micrometer记录 Counter / Timer / Gauge
→
Actuator暴露 /actuator/prometheus
→
Prometheus定时 scrape + 存储
→
Grafana查询 + 面板 + 告警
k6 负责制造负载；Prometheus 负责记录；Grafana 负责展示。三者不是同一个东西。

P50 / P95 / P99 怎么理解？

选择不同负载，观察单/双实例在同一入口下的真实结果。P95=95% 的请求不超过该延迟，剩余 5% 更慢。

为什么不能只看平均值？

平均值会被少数极慢请求稀释。比如 99 个 5ms、1 个 2s，平均值约 25ms，但 P99 接近 2s。用户抱怨的往往正是尾部请求。

dropped iterations 是什么？

k6 计划每秒发起 N 个请求，但因为机器 CPU、网络或 VU 不够，实际没有按时发起。它说明“压测机或调度器本身可能成为瓶颈”，此时实际 RPS 和延迟都要谨慎解释。

阶段 1：SQL、N+1、分页与搜索

这一阶段解决的是“数据库做了很多不该做的重复劳动”。

为什么集合 JOIN + Page 危险？

文章和标签是一对多/多对多。直接 JOIN FETCH 后分页，数据库返回的行数会被集合放大；Hibernate 为了得到正确分页结果，可能加载大量记录后在内存里处理。数据量大时不仅慢，还可能出现计数和分页异常。

两段式分页怎么做？

  1. 先查当前页的文章 ID；
  2. 再按 ID 批量加载作者、标签；
  3. 按原 ID 顺序组装返回。

多一次批量查询，但避免了集合 JOIN 放大和不稳定分页。

N+1 查询可视化

拖动一页笔记数量，观察“循环逐条查评论”的 SQL 次数。

43修复前 SELECT/请求
4修复后 SELECT/请求
39减少次数
N+1 的准确定义：先查出一页主对象（1 次），再在循环里对每个对象查关联数据（N 次）。解决思路不是“把循环写快”，而是收集当前页 ID，一次批量查关联数据，再按 ID 分组回装。

笔记评论的查询顺序

1. 分页查 notes只拿当前页 noteId
↓
2. 批量查 commentsWHERE note_id IN (...)
↓
3. 批量查评论作者一次加载用户信息
↓
4. 批量查当前用户点赞一次查询点赞状态
↓
5. 按 noteId 分组 → 建树 → 截取前 3 条根评论截断在建树之后、返回之前
为什么“先建树再截断”？

评论有父子层级。直接截取原始评论可能截到子评论，导致根评论数量或树结构不完整。先按 noteId 分组并建树，再从根节点列表截取前 3 条更符合业务语义。

FULLTEXT 与 Elasticsearch 怎么选？

维度MySQL FULLTEXTElasticsearch

“不用 ES”不是不会 ES，而是当前业务没有复杂到值得承担同步和运维成本。数据量、中文分词、相关性排序需求明显增长后再评估。

为什么第一次请求查 MySQL，后面才命中 Redis？

第一次是 cache miss：Spring Cache 拦截后没有读到值，执行原方法查 MySQL，再把结果写回 Redis。第二次相同 Key 才能命中。Redis 故障时，统一包装层会让流程继续执行 loader，避免方法体还没跑就抛异常。

TTL 随机抖动

如果大量 Key 同时 10 分钟过期，会在同一秒集中回源。TTL 加随机抖动可以把过期时间打散，避免周期性的数据库尖峰。

精确失效

更新文章时不使用 allEntries=true 清空整个 cache，而是通过版本号或明确的 Key 让相关缓存失效，减少无关缓存被击穿。

缓存 Key 维度

分页、标签、语言、搜索词等业务维度必须进入 Key。否则第 1 页和第 2 页会互相覆盖，不同筛选条件也可能读到错误数据。

Redis 故障语义

核心页面缓存：回源 MySQL；在线人数：返回 0；留言限流：fail-open；登录防护：fail-open；浏览量：允许少计；分布式锁：失败则跳过任务。不同业务不能套同一个策略。

热点 Key 回源与分布式锁

同一 Key 在缓存失效瞬间可能有大量并发请求。点击演示，观察单实例和多实例的处理差异。

当前设计不是严格全局单飞：单实例内有强互斥；多实例抢不到 Redis 锁时，为了可用性允许继续回源。严格单飞需要等待、二次检查和超时降级，会增加延迟。

不能把 Redis 和 MySQL 当成一个事务：用稳定 batchId 和 MySQL 唯一键防重复，比“先 MySQL 后 Redis”更可靠。进程崩溃后同一 batch 重试不会重复加浏览。

为什么 Hikari 连接池不是越大越好？

Hikari 管理到 MySQL 的物理连接。连接太多会把压力推给数据库，增加锁竞争和上下文切换。项目通过 pending/acquire 指标，把 10 连接调整为 min10/max20。

为什么 Redis 挂了，部分业务仍会失败？

统一缓存包装只覆盖核心 @Cacheable 读路径。浏览量、在线人数、限流、登录防护和分布式锁使用直接 RedisTemplate，必须各自定义 fail-open / fail-closed / 跳过任务，不能盲目套用缓存回源。

阶段 3：RabbitMQ 可靠异步链路

重点不是“会发消息”，而是理解消息怎样路由、何时确认、失败去哪里、重复怎么处理。

Producer 是怎么到 Exchange 的？

生产者发送时明确指定 Exchange 名称和 Routing Key，不是直接“绑定到队列”。生产者通常不知道有哪些 Queue；Exchange 根据自身类型、Routing Key 和 Binding 决定投递到哪些 Queue。

Publisher Confirm 是什么？

方向是 Broker → Producer：Broker 告诉生产者“消息已经收到并负责了”。它不表示消费者已经处理，更不表示 MySQL 已经落库。

Consumer ACK 是什么？

方向是 Consumer → Broker：消费者完成业务处理后告诉 Broker 可以删除消息。手动 ACK 必须放在数据库事务提交成功之后。

为什么访问日志允许丢？

生产端 fail-open：RabbitMQ 不可用时业务请求仍正常返回，只记录 publish failure 指标。访问日志不是核心交易数据，当前允许短暂丢失；零丢失需要 Outbox。

为什么必须幂等？

消息系统通常至少一次投递。生产者重试、网络抖动、消费者重连都可能造成同一消息重复到达。消费端用 eventId 唯一键防重复写库。

为什么不是简单全部重试？

全部重试会让正常消息反复执行，增加数据库压力。二分拆批能逐步隔离坏消息，成功子批继续提交，最终只把永久失败消息送进 DLQ。消费端仍必须用 eventId 幂等兜底。

RabbitMQ 挂了，消息会不会自动补发？已经成功进入 Broker 且持久化的消息，在 Broker 恢复后通常还能被消费；但生产端 fail-open 期间根本没发出去的消息不会自动补发。要做到这一点，需要 Outbox 或本地事件表。

代码逐段走读：这些方案到底怎么落地？

每个标签页都按“代码在做什么 → 为什么这样写 → 边界是什么”解释。代码已做教学化简，不是完整文件。

NoteServiceImpl：当前页批量加载

List<String> noteIds = notes.stream()
    .map(Note::getId)
    .filter(Objects::nonNull)
    .toList();

List<NoteComment> allComments = noteCommentRepository
    .findByNoteIdInOrderByNoteIdAscCreatedAtAsc(noteIds);

Map<String, List<NoteComment>> commentsByNote =
    allComments.stream().collect(Collectors.groupingBy(
        NoteComment::getNoteId, LinkedHashMap::new, Collectors.toList()));

Map<String, User> userMap = loadUsers(allComments);

for (Note note : notes) {
    List<NoteComment> flat =
        commentsByNote.getOrDefault(note.getId(), List.of());
    note.setComments(buildCommentTree(flat, userMap)
        .stream().limit(3).toList());
}
代码在做什么：先收集当前页 noteId，再批量查评论和评论作者，按 noteId 分组后回装到每篇笔记。
为什么这样写：数据库查询次数从“1 + N”变成固定次数；只在当前页范围内查，不会把全表评论拉回来。
截断位置：先建完整评论树，再截取前 3 条根评论。否则可能把子评论截断，导致树结构不完整。

ResilientCache：把 Redis 异常变成 cache miss

@Override
public ValueWrapper get(Object key) {
    try {
        return delegate.get(key);
    } catch (RuntimeException ex) {
        onFailure("get", key, ex);
        return null;
    }
}

@Override
public void put(Object key, Object value) {
    try {
        delegate.put(key, value);
    } catch (RuntimeException ex) {
        onFailure("put", key, ex);
    }
}

private void onFailure(String op, Object key, RuntimeException ex) {
    meterRegistry.counter("cache.redis.failures",
        "cache", getName(), "operation", op).increment();
    if ("get".equals(op)) {
        meterRegistry.counter("cache.redis.fallbacks",
            "cache", getName()).increment();
    }
}
关键理解：get 失败返回 null，Spring Cache 会把这次当成“没命中”，继续执行原方法查 MySQL。
写回失败：put 失败只记录指标，不影响已经查到的业务结果。下一次请求再尝试写缓存。
边界：这只覆盖缓存读路径；浏览量、限流、在线人数、分布式锁仍各自处理 Redis 故障。

RedisDistributedLock：SET NX + token + Lua 释放

String token = UUID.randomUUID().toString();

Boolean acquired = redisTemplate.opsForValue()
    .setIfAbsent("blog:lock:" + name, token, ttl);

if (!Boolean.TRUE.equals(acquired)) {
    return null; // 锁被其他实例持有
}

// 释放时先比较 token，避免误删别人后来获取的锁
String lua =
    "if redis.call('GET', KEYS[1]) == ARGV[1] then " +
    "return redis.call('DEL', KEYS[1]) end; return 0";

redisTemplate.execute(RELEASE_SCRIPT, List.of(key), token);
SET NX：只有 Key 不存在时才能设置成功，这是获取锁的原子操作。
随机 token：标识锁的持有者。锁过期后即使原持有者回来，也不能误删新持有者的锁。
TTL：防止进程崩溃后锁永远不释放；任务必须明显短于 TTL。

ViewCountFlushServiceImpl：batchId 幂等

@Transactional
public BatchResult applyBatch(String batchId,
        String postId, long delta) {

    int inserted = batchRepository.insertIgnore(batchId, postId, delta);
    if (inserted == 0) {
        return BatchResult.ALREADY_APPLIED;
    }

    int updated = postRepository.incrementViewCount(postId, delta);
    if (updated == 0) {
        batchRepository.markSkipped(batchId);
        return BatchResult.POST_NOT_FOUND;
    }
    return BatchResult.APPLIED;
}
为什么先 INSERT：batchId 唯一键是幂等闸门。重复执行同一 batch 时 insertIgnore 返回 0，直接跳过累加。
为什么同一事务：登记批次和更新 view_count 必须一起提交或一起回滚，避免只做一半。
崩溃场景：若 MySQL 已提交但 Redis 未扣减，下次重试会识别 ALREADY_APPLIED，不会重复加浏览。

RabbitMQ：Confirm 发送 + 手动 ACK / NACK

// Producer：发送持久化消息
rabbitTemplate.convertAndSend(
    "blog.events", "visit.recorded", event,
    message -> {
        message.getMessageProperties()
            .setDeliveryMode(MessageDeliveryMode.PERSISTENT);
        return message;
    },
    correlationData);

// Consumer：数据库事务提交后再 ACK
try {
    persistWithRetry(events); // 批量事务写 MySQL
} catch (Exception ex) {
    processRange(items, from, mid, failedIndexes);
}

for (int i = 0; i < items.size(); i++) {
    if (failed.contains(i)) {
        channel.basicNack(deliveryTag, false, false); // → DLQ
    } else {
        channel.basicAck(deliveryTag, false);
    }
}
Confirm：Broker 对 Producer 的确认，只代表消息被 Broker 接收。
ACK：Consumer 对 Broker 的确认，代表业务处理完成；本项目要求在 MySQL 事务提交后 ACK。
失败：批量失败二分拆批，最终坏消息 NACK 到 DLX/DLQ；eventId 唯一键继续兜底重复消息。

        proxy_next_upstream error timeout http_502 http_503 http_504;
        proxy_next_upstream_tries 2;
    }
}
upstream：Nginx 把请求分给两个无状态 backend；JWT 放 Header/Cookie，不依赖 Sticky Session。
故障重试：backend-1 连接失败时尝试 backend-2。实测首次切换约 3 秒，之后请求恢复正常。
边界：单机双实例证明高可用和应用层并行，不等于两台独立服务器线性扩容。

为什么双实例没有稳定提升？

两个 JVM 在同一台电脑上，共享 CPU、内存、网卡、内核网络栈、MySQL、Redis 和 Nginx。第二个实例如果没有额外 CPU 预算，只会增加进程和上下文切换。

CPU 亲和性实验做了什么？

把 k6 固定在 CPU 0-3，backend-1 固定在 8-11，backend-2 固定在 12-15，再跑固定到达率。这样才勉强近似“给第二个实例额外计算资源”。

高频疑问总索引

这里集中解释你在项目过程中最常问、最容易混淆的地方。可以直接搜索关键词。

1. P95、P99 多少算优秀？

没有绝对答案。先看业务 SLO：页面接口一般希望 P95 在几十到几百毫秒；写接口还要看数据库和外部依赖。你的项目里，缓存命中读路径 P95 在低中压时只有几毫秒，高压下受共享 CPU、Redis、Nginx 和 k6 影响。判断时要同时看实际 RPS、错误率和 dropped iterations。

2. 数据好看是不是因为都打 Redis 了？

是重要原因。缓存命中路径几乎不查 MySQL，所以看起来非常快；这正说明缓存有效，但也意味着不能拿它证明数据库查询能力。正确做法是同时测缓存开启、缓存关闭和大数据量场景，并观察 MySQL QPS、慢查询、Hikari pending。

3. Hikari 到底是什么？和线程池一样吗？

Hikari 是 JDBC 连接池，管理应用和 MySQL 之间的物理连接。线程池管理的是执行任务的线程；Hikari 管理的是数据库连接。minimum-idle 不是核心线程数，maximum-pool-size 也不是最大线程数。

4. 为什么搜索用 FULLTEXT 而不是 ES？

当前搜索主要是标题、正文和标签，数据规模和相关性排序要求还不需要 ES。ES 会引入索引同步、双写一致性、集群和运维成本。先用 FULLTEXT 解决 LIKE 全表扫描，有明确复杂搜索需求后再评估 ES/OpenSearch。

5. 为什么 Redis 缓存能降级，但其他 Redis 操作不能统一降级？

不同业务故障语义不同。核心页面缓存失败可以查 MySQL；在线人数失败返回 0 可接受；留言限流失败应 fail-open；登录防爆破失败也是 fail-open，但安全性下降；分布式锁失败应该跳过任务，不能让多个实例同时刷库。统一包装只适合读缓存，不适合所有操作。

6. Spring Cache 默认 Redis 挂了到底会怎样？

默认情况下 Redis 连接失败可能抛 RedisConnectionFailureException，方法体还没执行。项目加了统一 ResilientCacheManager 后，get 失败会记录 fallback 指标并执行 loader，写回失败也不影响返回。这是项目自己的扩展行为，不是 Spring Cache 默认行为。

7. 热点 Key 为什么不是严格全局只回源一次？

严格全局单飞要求其他实例等待锁、拿到锁后二次检查缓存，并处理锁超时和 loader 超时。等待会增加延迟，Redis 本身故障时还可能拖死请求。当前采用可用性优先：单实例强互斥，多实例抢不到锁时允许少量重复回源。

8. 浏览量幂等为什么不能靠事务解决？

Redis 和 MySQL 是两个系统，本地事务无法覆盖跨系统命令。项目用稳定 batchId + MySQL 唯一键记录批次，同一批次重复执行不会重复加浏览；Redis 扣减放在数据库成功之后，失败时允许少计，不追求强一致。

9. N+1 的解决顺序到底是什么？

分页查笔记 → 收集当前页 noteId → 批量查评论 → 批量查评论作者 → 批量查点赞 → 按 noteId 分组 → 建评论树 → 截取前 3 条根评论。关键是一次只查当前页，不查全表。

10. Publisher Confirm 和 Consumer ACK 有什么区别？

Confirm 方向是 Broker → Producer，只表示 Broker 收到消息；ACK 方向是 Consumer → Broker，表示消费者完成处理。Consumer 要在 MySQL 事务提交后再 ACK。两者都存在也不代表“恰好一次”，消费端仍需 eventId 幂等。

11. RabbitMQ 故障期间，消息到底丢不丢？

已经成功进入 Broker 并持久化的消息通常能在恢复后继续消费；但 fail-open 期间根本没发送成功的访问日志不会自动补发，所以允许丢失。零丢失需要 Outbox：业务事务内写事件表，后台可靠投递。

12. 两个 JVM 为什么不一定更快？

两个 JVM 不等于两份 CPU、网卡和 MySQL。单机上它们共享资源，k6 还和被测系统抢 CPU。只有给应用更多有效计算资源，水平复制才可能表现为稳定容量提升。当前实验通过 CPU 亲和性隔离后才看到双实例优势。

13. MinIO 为什么单机也需要？

单实例本地文件没问题；两个实例在同一台机器也能暂时共享目录，但这不能代表跨机器部署。多实例一旦分到两台主机，本地 uploads 目录不共享，A 上传的文件 B 看不到。MinIO 把文件变成共享外部状态。

14. 故障矩阵一定要两个主机吗？

不一定。单机可以做应用级故障：停 Redis、停 RabbitMQ、停对象存储、优雅停机、杀一个 backend、验证 Nginx 切换。两个主机才能证明物理主机宕机、网络分区、独立硬件扩容和真正的多节点高可用。

15. 为什么访问日志只有一条链路进入 RabbitMQ？

目标是把一条链路做完整，验证 Publisher Confirm、手动 ACK、批量事务、eventId 幂等、重试和 DLQ。把邮件、点赞、缓存失效、搜索索引全部塞进去会大幅增加复杂度，但不会增加面试价值。

术语词典

把缩写和概念用一句话说清楚。

Actuator

Spring Boot 的管理端点，暴露 health、metrics、prometheus 等信息。

Micrometer

Java 指标门面，记录 Counter、Timer、Gauge，并适配 Prometheus。

Prometheus

负责定时抓取和存储时间序列指标的监控系统。

Grafana

查询监控数据并绘制面板、配置告警的可视化工具。

P95 / P99

95%/99% 请求不超过的延迟值，用于观察尾部性能。

HikariCP

高性能 JDBC 数据库连接池，不是线程池。

N+1

1 次主查询加 N 次循环关联查询，典型 ORM 性能问题。

FULLTEXT

MySQL 全文索引，用于替代低效的 LIKE 全表扫描。

TTL Jitter

给缓存过期时间加随机抖动，避免大量 Key 同时失效。

Cache Stampede

热点 Key 失效瞬间大量请求同时回源数据库。

Idempotency

同一操作重复执行多次，最终结果与执行一次相同。

Publisher Confirm

RabbitMQ Broker 告诉 Producer 消息已接收。

Consumer ACK

消费者完成处理后告诉 Broker 可以删除消息。

DLQ

死信队列，存放重试耗尽或无法处理的坏消息。

Fail-open

附属能力故障时放行主业务，例如 MQ 日志或限流失败时不阻断请求。

Outbox

业务事务内先写事件表，再可靠投递到 MQ 的模式，可降低消息丢失。

MinIO / S3

对象存储协议和实现，用 bucket/key 管理共享文件。

Graceful Shutdown

停止接收新请求，等待当前请求和消费者任务处理完成再退出。
