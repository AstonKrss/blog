# 阶段 4 单机资源隔离与扩容验证报告

> 日期：2026-11-10  
> 范围：单台 Windows 电脑上的 Nginx `8088` 入口、两个 Spring Boot 实例、共享 MySQL/Redis/RabbitMQ  
> 目标：回答“只有一个电脑时，双实例到底有没有性能提升”

---

## 1. 结论先行

在当前单机环境下，结论分成三层：

1. **双实例确实能利用更多 CPU 并改善高负载稳定性。**  
   在 CPU 资源分组后，双实例能稳定跑满 1000/1500 RPS，`dropped_iterations=0`；单实例只使用一组 CPU 时会明显排队、掉迭代，P95 波动很大。

2. **不能据此声称“生产环境性能翻倍”。**  
   k6、Nginx、MySQL、Redis、RabbitMQ 和两个 JVM 仍然共享同一台物理机、同一块网卡和同一套内核网络栈。这里证明的是“增加应用可用 CPU 能改善该单机实验”，不是“两台独立服务器线性扩容”。

3. **关闭缓存后双实例仍然有收益，但共享 MySQL/中间件让尾部延迟波动明显。**  
   两次 500 RPS 对照中，双实例都保持 `dropped_iterations=0`，单实例分别出现 47 和 143 次 dropped iterations。双实例 P95 分别为 8.69 ms 和 273.87 ms，单实例分别为 73.79 ms 和 475.91 ms。

因此，阶段 4 可以按“**单机可验证范围完成、真实多机扩容与共享存储验收延期**”收口，不能把结果写成夸大的线性扩展结论。

| 项目 | 配置 |

| 机器 | 单台 Windows 电脑，16 个逻辑处理器 |
| 后端 | Spring Boot 同 jar，8081/8082 |

| 接口组合 | 文章第 1/2 页、标签、归档、搜索、统计 |
| 单次时长 | 30 秒；每模式先做 10 秒 100 RPS 预热 |

### 2.1 CPU 分组

为避免“两个 JVM、k6 和中间件互相抢同一组 CPU”导致结果失真：

| 进程 | CPU | 亲和性掩码 |
|---|---|---:|
| k6 | CPU 0-3 | `000F` |
| backend-1 | CPU 8-11 | `0F00` |
| backend-2 | CPU 12-15 | `F000` |
| MySQL / Redis / RabbitMQ / Nginx | 未独占，可竞争其余 CPU | - |

> 局限：中间件没有做完整 cgroup/CPU 隔离，因此 CPU 4-7 仍可能与 WSL、MySQL 或系统进程竞争。

## 3. 缓存开启场景

### 3.1 测试结果

使用 `loadtest/k6/stage4-constant.js`，固定到达率，分别重复两轮。

| 目标 RPS | 模式 | 轮次 | 实际 RPS | P95 | P99 | Dropped |
|---:|---|---:|---:|---:|---:|---:|
| 1000 | 单实例 | 1 | 904.89 | 2076.98 ms | 2457.65 ms | 2107 |
| 1000 | 单实例 | 2 | 958.00 | 1284.92 ms | 2008.13 ms | 948 |
| 1000 | 双实例 | 1 | 999.83 | 63.95 ms | 596.12 ms | 0 |
| 1000 | 双实例 | 2 | 999.91 | 45.02 ms | 283.21 ms | 0 |
| 1500 | 单实例 | 1 | 1499.86 | 26.39 ms | 737.44 ms | 0 |
| 1500 | 单实例 | 2 | 1409.17 | 1935.43 ms | 2299.95 ms | 1320 |
| 1500 | 双实例 | 1 | 1499.84 | 5.17 ms | 188.60 ms | 0 |
| 1500 | 双实例 | 2 | 1460.57 | 6.92 ms | 212.21 ms | 0 |

### 3.2 解读

- 双实例两轮都完成目标压力，`dropped_iterations=0`。
- 单实例在 1000 RPS 两轮都掉迭代；1500 RPS 一轮正常、一轮严重掉迭代，说明单组 CPU 下的结果非常依赖瞬时调度和共享资源竞争。
- 双实例 P95 在 1500 RPS 两轮分别为 5.17 ms 和 6.92 ms，表现稳定。
- 不能把 1000 RPS 的 P95 直接做精确百分比对比，因为单实例出现了负载生成器/调度器层面的 dropped iterations，实际到达率本身没有达标。

### 3.3 关键发现

之前“双实例没有提升”的主要原因是：

> 两个 backend 虽然启动了，但第二个实例没有获得独立 CPU 预算；k6、JVM、Nginx 和中间件全部在同一资源池竞争。

给两个实例分配不同 CPU 组后，双实例开始表现出更稳定的吞吐能力。这不是 Nginx 配置问题，而是单机资源竞争导致的可测性问题。

## 4. 关闭缓存场景

### 4.1 测试结果

`BLOG_CACHE_ENABLED=false`，请求强制走 MySQL 和业务查询路径。

| 目标 RPS | 模式 | 轮次 | 实际 RPS | P95 | P99 | Dropped |
|---:|---|---:|---:|---:|---:|---:|
| 200 | 单实例 | 1 | 199.99 | 64.86 ms | 297.13 ms | 0 |
| 200 | 双实例 | 1 | 200.01 | 8.86 ms | 465.25 ms | 0 |
| 500 | 单实例 | 1 | 498.38 | 73.79 ms | 1033.46 ms | 47 |
| 500 | 单实例 | 2 | 495.21 | 475.91 ms | 1334.69 ms | 143 |
| 500 | 双实例 | 1 | 499.97 | 8.69 ms | 134.77 ms | 0 |
| 500 | 双实例 | 2 | 499.97 | 273.87 ms | 612.16 ms | 0 |

### 4.2 解读

- 200 RPS 双实例的 P95 更低，但 P99 反而更高，说明少量请求仍然受到共享 MySQL/连接池/系统调度影响。
- 500 RPS 两轮中，双实例都没有掉迭代，单实例都出现掉迭代。
- 双实例 P95 波动很大（8.69 ms 到 273.87 ms），说明此时瓶颈已经不只是应用 CPU，还包括：
  - 单台机器上的 MySQL；
  - Hikari 连接池；
  - WSL 网络转发；
  - Windows 文件系统与页面缓存；
  - k6 仍与被测系统共享硬件。
- 因此关闭缓存场景只能证明“双实例在应用侧有并行收益”，不能证明数据库层可以无限扩展。

## 5. 与之前未做 CPU 隔离的结果对比

### 5.1 未做 CPU 隔离

之前同一入口固定到达率结果：

| 目标 RPS | 单实例 P95 | 双实例 P95 | 观察 |
|---:|---:|---:|---|
| 500 | 5.33 ms | 3.93 ms | 双实例略好 |
| 1000 | 152.74 ms | 190.84 ms | 双实例更差 |
| 1500 | 1267.98 ms | 1411.18 ms | 双实例更差 |

### 5.2 做 CPU 隔离后

- 双实例在 1000/1500 RPS 两轮都稳定完成；
- 单实例多次出现 dropped iterations 和明显长尾；
- 说明未隔离时“双实例更差”的结论不能直接用于生产容量判断。

### 5.3 最终解释

```text
两个 JVM != 两份 CPU
两个 JVM != 两张网卡
两个 JVM != 两个 MySQL
两个 JVM != 独立压测机
```

只有在应用侧确实获得额外 CPU 预算时，双实例的并行处理才有机会体现；否则第二个 JVM 只是增加了进程数、内存占用和上下文切换。

## 6. 这份报告能支持什么结论

可以写：

> 在单机资源隔离实验中，通过 Nginx 对两个 Spring Boot 实例进行分流，并为 k6 与两个 JVM 分配不同 CPU 组，双实例在 1000/1500 RPS 固定到达率下均无 dropped iterations；单实例在高负载下出现明显 dropped iterations 和长尾延迟。该实验验证了应用层水平复制的有效性，同时暴露了单机压测对共享中间件和负载生成器的依赖。

不能写：

> 双实例性能提升 100%。

也不能写：

> 双实例可以无限扩展。

## 7. 已知不足与延期项

以下项目不在本轮单机实验中伪造完成，统一列为后续工作：

1. **独立压测机**  
   当前 k6 和被测应用共享同一台电脑。即使做了 CPU 亲和性，也无法完全排除调度、网卡、内存带宽和系统中断干扰。

2. **两台独立应用节点**  
   当前两个 JVM 在同一台物理机上。真正的水平扩容需要在两台独立服务器或至少两个独立资源边界的节点上复测。

3. **中间件完整隔离**  
   MySQL、Redis、RabbitMQ 和 Nginx 未做 cgroup/CPU 独占，仍是共享瓶颈。

4. **样本量**  
   缓存开启场景完成两轮；关闭缓存场景 200 RPS 一轮、500 RPS 两轮。正式容量报告建议每个关键场景至少 3 轮取中位数。

5. **MinIO 真实共享文件验收**  
   代码已有 MinIO 抽象，但尚未完成真实 MinIO 上传、双实例读取和 MinIO 停机恢复演练。

6. **双实例可观测性**  
   Prometheus/Grafana 还需要区分 8081/8082 实例，补齐双实例 HTTP、Hikari、JVM 和队列指标。

7. **完整故障矩阵**  
   Redis 停止 30 秒、RabbitMQ 停止/恢复、MinIO 停止、优雅停机、单实例宕机后的业务指标恢复时间仍需要统一成自动化演练结果。

8. **定时任务双实例互斥验收**  
   分布式锁代码已存在，但仍需要记录“双实例同时到点只有一侧执行”的实际任务日志和指标证据。
